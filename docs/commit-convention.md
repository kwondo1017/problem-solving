# 커밋 컨벤션

## 기본 형식

```text
<type>(<scope>): <problem-id> <description>
```

예시: `solve(lc): 0001 two-sum`

문제와 무관한 문서·환경 변경은 문제 번호를 생략합니다.

```text
<type>(<scope>): <description>
```

예시: `docs(ps): 커밋 규칙 문서 작성`

타입과 스코프는 아래 표의 영문 식별자를 사용합니다. 커밋 제목의 설명과 본문은 한글로 작성하되, 플랫폼 식별자와 문제 이름·코드 이름은 원문을 유지합니다. 따라서 문제 이름만으로 설명하는 `solve(lc): 0001 two-sum`도 허용합니다.

## Scope 규칙

| Scope | 의미 |
| --- | --- |
| `lc` | LeetCode |
| `boj` | 백준 |
| `ps` | 저장소 전체 및 공통 설정 |

## Type 규칙

| Type | 용도 | 예시 |
| --- | --- | --- |
| `solve` | 새로운 문제 풀이 추가 | `solve(lc): 0001 two-sum` |
| `test` | 테스트 코드만 추가·수정 | `test(lc): 0001 경계 조건 추가` |
| `fix` | 기존 풀이의 오류 수정 | `fix(lc): 0001 인덱스 처리 오류 수정` |
| `refactor` | 정답과 동작을 유지하며 구현 개선 | `refactor(lc): 0001 조회 로직 단순화` |
| `docs` | 문서 작성 및 수정 | `docs(ps): 커밋 규칙 문서 작성` |
| `chore` | 개발 환경 및 저장소 관리 | `chore(ps): clang-format 설정` |

`solve`는 표준 Conventional Commits에서 필수로 정의하는 타입은 아니지만, 사용자 정의 타입으로 사용합니다. PS 저장소에서는 새로운 문제 풀이를 추가한다는 목적을 `feat`보다 명확하게 표현합니다.

### 풀이와 테스트를 함께 변경하는 경우

- 새 문제 풀이와 해당 테스트 코드를 한 커밋에 추가하면 `solve`를 사용합니다.
- 테스트 코드만 추가·수정하면 `test`를 사용합니다.
- 기존 풀이의 오류를 수정하면서 테스트를 추가·수정하면 `fix`를 사용합니다.
- 기존 풀이의 정답과 동작을 유지하며 구현을 개선하면 `refactor`를 사용합니다. 관련 테스트를 함께 변경해도 같은 타입을 사용합니다.

이 기준은 테스트 코드의 위치와 무관하게 적용합니다. 현재처럼 풀이 파일 내부에 테스트를 작성해도 테스트 코드만 변경하면 `test`입니다. 추후 별도 `test` 디렉터리를 도입하는 경우에도 같은 기준을 적용하며, 디렉터리 도입 여부는 아직 확정하지 않습니다.

## 문제 번호

- LeetCode는 최소 4자리로 표기합니다. 예를 들어 `1`은 `0001`, `12345`는 `12345`로 작성합니다.
- BOJ는 앞에 0을 붙이지 않고 원래 문제 번호를 사용합니다. 예시: `solve(boj): 1931 회의실 배정`
- 이 규칙은 커밋 제목에만 적용합니다. 기존 파일명과 파일명 규칙은 변경하지 않습니다.

## 커밋 단위

- 풀이 변경은 문제 하나를 커밋 하나의 단위로 합니다. 해당 변경에 필요한 테스트와 설명은 함께 포함합니다.
- 같은 문제의 후속 수정은 별도 커밋으로 남깁니다.
- 환경과 구조 변경은 관련 파일을 하나의 목적에 맞춰 묶습니다.
- 기존 커밋 이력은 보존하며, 새로 작성하는 커밋부터 이 규칙을 적용합니다.
